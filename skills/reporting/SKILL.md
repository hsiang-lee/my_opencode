# Reporting — 面向人类的汇报与请示

读者是忙人。他读完要在 5 秒内知道三件事：**现在是什么状态 / 要不要我动手 / 有什么风险**。

写成什么样由内容决定，不是填空。

---

## 结构（默认形状，哪块没有就删掉）

- **结论**：一句话。做完了什么、卡在哪、或者发现了什么。
- **需要你**：只在真有事情要对方做时出现。一个问题、2–3 个选项、你建议哪个、不回会怎样。
- **风险 / 未解决**：只在有时出现。说清后果和触发条件。
- **依据**：一行。测试数字、链接。放最后，不抢注意力。

规则：

- 没有「需要你」就整段不出现，**不写「需要你：无」**。
- ≤3 行能说完，就用纯文本，不加小标题。
- 一次只抬一个决策；多个待决时，只把最关键的放前面，其余给默认值。
- 可默认的请示写成「我按 X 做，你不回我就执行；不要就说停」。

---

## 信息保全（优先于格式）

任何会改变读者下一步判断的事实都必须出现，即使上面没有对应区块：风险、未验证的假设、副作用、阻塞、需要对方配合的动作、影响范围。

宁可多一行，不能漏。**格式服从内容，不是内容服从格式。**

---

## 写人话

| 别写 | 写成 |
|---|---|
| 「已完成」「当前状态」「其余 N 个字段」 | 「改好了」「还剩 1 个没解决」 |
| 「本地仓库未受影响」 | 「本地没动」 |
| 「要不要做，你说」（埋在段尾） | 放到最前面：「要做的话说一声」 |
| 逐条罗列实现细节 | 一句变化 + 一句影响 |

用读者听得懂的名词。他要细节会自己问。

---

## 不要转发内部件

子 agent 的报告是给编排者验收用的：SHA、文件清单、字段表、AC 矩阵、台账。**转述给人类时必须重写**，只留结论、影响、需要对方做的事。

## 三组对照

**1）做完了，无需对方动作**

> ❌ 仓库设置已改：squash 合并后的标题取 PR 标题，正文取 PR 正文。字段：`squash_merge_commit_title` `COMMIT_OR_PR_TITLE` → `PR_TITLE`……本地仓库没有受影响：在 main 分支，HEAD 为 `181d3dc`，工作区仍是那 5 项。

> ✅ 设置改完了，以后 squash 提交的正文取 PR 正文，不会再出现 1600 行的提交信息。历史里那 11 条超长提交我没动——清理要重写已发布历史，不划算，要清你说一声。

**2）做完了，但要对方配合**

> ❌ 改完了：182 pass，commit `1895fb5`，dist 已重建。现在的行为：- 正文改用 markdown 元素……- 容量：中文约 9200 字……生效方式：重启 opencode TUI。

> ✅ 改完了，手机卡片能正常渲染换行、列表和代码块，超长会明确标注已截断。
> 唯一要你做的：重启 opencode TUI，改动才生效。
> 还有一个没解决：手机端提问会退化成「请在 TUI 回答」。下次遇到时把那行日志给我，我来修。

**3）卡住了**

> ❌ 尝试了 A 方案和 B 方案，A 因为 X 失败，B 因为 Y 失败，另外环境里 Z 也不满足，所以目前无法继续。

> ✅ 卡在权限：飞书应用没有 `im:message:readonly`，读不到回复。你给我开这个权限，或者我改成轮询通知（体验差一点，但能跑）。

## 不适用

- 用户明确要「完整报告 / 详情 / 全部列出来」→ 按他要的给，不要擅自压缩。
- 子 agent 之间的结构化报告（台账、评审清单、验收证据）→ 不受本 skill 约束。
- PR 正文 → 按仓库约定（What / Why / Tested，≤5 行）。
