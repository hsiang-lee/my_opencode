# 重构即设计 — 稳定中间形式与留白

回到索引: [../SKILL.md](../SKILL.md)

> 设计不是一次画完的蓝图。设计只做**最小决策**（目标、契约、留白），结构由重构在坏味道出现时长出来。

## 一、四本书的同一论断

| 来源 | 论断 | 对本流程的含义 |
|------|------|----------------|
| Beck《Extreme Programming Explained》 | 简单设计：能跑、无重复、表达清晰、最少元素 | 先到最直白可工作的形态 |
| Fowler《Refactoring》 | 重构是「不改变可观察行为的结构调整」 | 结构变更单独一步，行为由测试锁死 |
| Evans《Domain-Driven Design》 | 模型在迭代中深化，不是前置产物 | 概念稳定前不预设类图 |
| Booch《Object Solutions》 | 复杂系统演化需要**稳定的中间形式** | 每步都停在可交付、可测试的形态 |

共同结论：**预先设计**（一步到位画全结构）在需求未稳定时必然返工；替代方案是小步走 + 及时重构。

## 二、稳定中间形式

**定义**：一个能被测试、能上线、无已知坏味道的形态；它不是最终结构，但不需要猜未来。

- 允许「重复两次」存在：第一次直接写，出现**第二次变化**时才提取抽象。
- 允许「分支两个」存在：分支 ≥3 处或第二个真实变体落地时才上多态。
- 每次到达稳定中间形式 → 提交、跑全量测试 → 再决定下一步。

判据：现在停下，代码是否仍可读、可测、可改？是 → 这就是合法中间形式。

## 三、留白清单（设计阶段的唯一增量）

设计阶段不预选模式，只记录「本可以引入抽象」的位置，留给重构时按坏味道决策。

| 字段 | 写法 |
|------|------|
| 位置 | `file:line` 或职责名 |
| 可能的变体 | 已知的 ≥1 个真实变体（无真实变体则写「无，观察中」） |
| 现在为什么不抽 | 只有 1 个实现 / 分支 <3 处 / 契约未稳 |
| 触发条件 | 出现第 2 个实现、分支到第 3 处、或契约变更时回看 |

平凡改动无需留白清单。留白清单不是 TODO 配额，不设「必须清空」的期限。

## 四、反例（照着做必错）

- **反例 1：预先设计** —— 需求评审时画出 Strategy + Factory + 三层接口，第一个迭代结束只有一个实现。
- **反例 2：为「以后可能会变」预留** —— 接口数 > 真实变体数，抽象成本永久存在而收益为零。
- **反例 3：设计文档当验收** —— 结构符合文档但坏味道仍在；验收应看测试与坏味道，不看图。
- **反例 4：重构混进行为变更** —— 同一提交既改结构又改行为，测试红了无法定位是哪一个。
- **反例 5：留白清单变成欠债借口** —— 明知第二次变化已发生仍不抽象，坏味道扩散。

## 五、与主流程的接法

1. 设计：目标 / 非目标 + 接口契约（前置 / 后置 / 不变式）+ 留白清单。
2. 实现：TDD 先到最直白形态；测试锁行为。
3. 重构：扫描坏味道 → 只做一种手法 → 测试保持绿。
4. 回看留白清单：触发条件命中才抽象，过 YAGNI 三问。
