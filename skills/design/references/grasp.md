# GRASP 九模式 — 职责分配的完整判据

回到索引: [../SKILL.md](../SKILL.md)

> 面向对象设计首先是「职责分配」，其次才是「结构模式」。九个模式不是设计模板，是九个提问角度。

## 1. Information Expert（信息专家）

**问题**：这个职责该给谁？
**判据**：谁拥有完成职责所需的**全部信息**，就分配给谁。
**正例**：`Order.total()` 自己算（它拥有 items）；`Cart.add(item)` 自己维护数量。
**收益**：低耦合（不跨类取数）、高内聚（数据与行为同处）。
**反例**：`OrderCalculator.calculate(order)` 从 Order 扒光字段 —— 这是 A5 贫血模型。
**注意**：信息专家不是「数据在哪就全塞哪」。若有多个专家，拆成协作，由编排者组合。

## 2. Creator（创建者）

**问题**：谁负责 new？
**条件**（满足其一即可）：聚合（B 是 A 的组成部分）/ 包含 / 持有初始化所需数据 / 记录实例 / 频繁使用。
**优先级**：聚合 > 包含 > 拥有初始化数据 > 记录实例 > 频繁使用。
**补充**：创建逻辑复杂（条件分支、配置驱动）→ 引入 Factory（见 `gof.md`），别让 Creator 变成巨型 switch。

## 3. Controller（控制器）

**问题**：系统事件（UI 动作、API 请求、消息）谁接收？
**判据**：用**薄**控制器接收并转译，再委托给领域对象。控制器只做：参数解析/校验 → 调用 → 组装响应。
**反例**：Controller 里写业务规则、拼 SQL、做计算。
**两种形态**：用例控制器（一个用例一个类）/ 外观控制器（一个子系统一个入口）。

## 4. Low Coupling（低耦合）

**问题**：怎么让改动不引发连锁反应？
**手段**（按性价比排序）：依赖接口而非具体类 → 减少不必要引用 → 缩小可见性 → 优先不可变 → 用事件替代直接调用。
**判据**：改动一个类，需要同时改的类 ≤ 1。
**注意**：低耦合不是零耦合，必要的协作必须有连接。与高内聚一起看。

## 5. High Cohesion（高内聚）

**问题**：一个类该承担多少？
**判据**：类内所有职责**相关且一起变化**；类的名字能一句话概括全部职责而不出现「和」。
**反例**：一个类同时管鉴权、日志、折扣计算。
**信号**：类的部分方法完全不使用类的多数字段 → 那部分该搬走。

## 6. Polymorphism（多态）

**问题**：行为随类型变化怎么办？
**判据**：用多态分发替代 `if/else`、`switch`、`dynamic_cast`、`instanceof` 的类型分支。
**对应**：Strategy / State / Template Method / Factory Method 的底层机制。
**注意**：分支只有 2 个且稳定时不值得上多态（YAGNI）。

## 7. Pure Fabrication（纯虚构）

**问题**：职责不属于任何领域对象怎么办？
**判据**：为降低耦合或提高复用，**造一个业务里不存在的类**来承接。
**典型产物**：Repository、Service、Gateway、Mapper、Adapter、Policy、Specification。
**注意**：纯虚构是妥协不是目标。虚构类太多 = 领域模型太弱，先回头看 Information Expert。

## 8. Indirection（间接性）

**问题**：两个类不该直接认识却要协作？
**判据**：中间插一层，让双方只依赖中间层。
**形态**：接口、事件总线、Mediator、Facade、消息队列、防腐层（ACL）、回调。
**代价**：多一跳、多一个概念。只在不稳定或跨边界处使用。

## 9. Protected Variations（防止变异）

**问题**：哪里将来会变？怎么把变化挡住？
**判据**：识别已经出现或明确排期的变化点 → 藏到稳定接口后面。
**形态**：策略接口、适配层、插件机制、配置驱动、数据驱动。
**红线**：**不能拿它预测未来**。「也许会变」不算变化点 → 违反 YAGNI。

## 常见分配错误 → 修正

| 错误 | 表现 | 修正 |
|------|------|------|
| 贫血模型 | Entity 只有 getter/setter，业务在 Service | Information Expert 收编行为 |
| 万能 Service | `XxxService` 什么都写，上千行 | 拆小；领域行为回实体，跨聚合才留 Service |
| 胖 Controller | 业务规则全在 Controller | 下沉到领域层，Controller 只做转译 |
| 满屏 `if (type)` | 类型分支散落多处 | Polymorphism + Strategy/State |
| SDK 散落业务 | 第三方调用遍布业务代码 | Pure Fabrication + Protected Variations（适配层） |
| 过度抽象 | 一个接口一个实现，永不变 | 过 YAGNI 三问再引入 |

## 附：为什么「职责分配」有效（Booch 的复杂系统五属性）

| 属性 | 含义 | 对设计的直接含义 |
|------|------|------------------|
| 层次结构 | 系统由子系统嵌套而成 | 分层与分包，不要平铺 |
| 相对本原 | 什么是「基础组件」取决于抽象层次 | 同一概念在不同层可有不同粒度 |
| 分离关注 | 内部紧密、外部松散 | 高内聚低耦合的源头 |
| 共同模式 | 少数结构反复出现 | 模式是经验复用，不是发明 |
| 稳定的中间形式 | 演化需要中间稳定层 | 小步重构，不做一步到位的大改 |

对象模型七要素：抽象、封装、模块化、层次结构、类型（前四为传统 OO 核心）+ 并发、持久（工程扩展维度）。评审时可问：这套设计在哪一层抽象上成立？换一层还成立吗？
