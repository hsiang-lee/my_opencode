# 分析模型 — 用例、领域模型与 UML 最小集

回到索引: [../SKILL.md](../SKILL.md)

> 分析问「系统该做什么」，设计问「职责落在谁头上」。两者是**连续迭代**关系：分析结论在编码中回补，设计暴露的缺口反过来修正需求。

## 1. 用例模型

- **做什么**：列出参与者（Actor）与目标，每条用例写「谁 → 想达成什么 → 成功判据」。
- **最小产出**：用例名 + 主成功场景（3–7 步）+ 关键异常分支。不要写界面细节与类名。
- **判据**：用例描述里出现「调用 XxxService」= 已经越界到设计，删掉。

## 2. 领域模型

| 元素 | 判据 |
|------|------|
| **Entity** | 有身份与生命周期，同一身份不同状态仍是同一对象 |
| **值对象** | 无身份、不可变、按值相等（Money、DateRange、Address） |
| **聚合边界** | 一个事务内必须一致的最小对象集；外部只能引用聚合根 |

- 领域模型只画**概念与关系**（多重性、约束），不画方法签名与表结构。
- 聚合边界从**一致性需求**推出来，不从数据库外键推出来。

## 3. 交互图选型

| 图 | 何时用 |
|----|--------|
| **顺序图** | 需要看清调用**时序**、条件分支、消息先后（多数场景首选） |
| **通信图** | 对象多、重点是**结构连接**而非时序；或用例步骤少、关注协作拓扑 |

- 一条用例配一张顺序图即可，不要给每个方法画图。
- 图里出现「new 具体实现类」→ 依赖方向可疑，回 `solid-packages.md` 检查。

## 4. 从分析到设计的过渡判据

| 阶段 | 只回答 | 不该出现 |
|------|--------|----------|
| 分析 | 概念、职责候选、协作关系 | 具体类名、接口签名、模式名 |
| 设计 | 职责分配、接口契约、依赖方向 | 数据库表、框架注解 |

**职责分配发生在设计，不在分析。** 分析阶段写「订单需要计算总价」，设计阶段才决定 `Order.total()` 还是 `PricingService`（判据见 `grasp.md`）。
**过渡信号**：概念稳定、多重性明确、用例主场景无争议 → 可以开始分配职责；否则回补需求，不要在模型上加抽象掩盖模糊。

## 5. 常见误用

| 误用 | 后果 | 应对 |
|------|------|------|
| 分析模型直接当设计模型 | 概念类变成贫血 Entity + 巨型 Service | 重新分配职责，过 A5 判据 |
| 先画模式类图再找需求 | 为模式找问题 | 先写用例与领域模型，模式只在坏味道出现后引入 |
| 领域模型里塞 getter/setter | 模型退化成数据表 | 只画概念与约束，行为在设计阶段补 |
| 给每个用例画全套 4+1 视图 | 文档成本压过收益 | 只留用例 + 领域模型 + 关键顺序图 |
| 聚合边界按表关系划分 | 跨聚合强一致、事务过大 | 按一致性需求划，跨聚合用最终一致 |

> A5 贫血模型等坏味道的识别与首选手法见 [`../../refactoring/references/smells-catalog.md`](../../refactoring/references/smells-catalog.md)。

## 6. 本流程七步（连续迭代）

分析不是一次性阶段，按步推进，任一步信息不足就回上一步。与 Larman 的 UP 序列不同：本流程省去系统顺序图与操作契约，末步是测试循环而非设计交接——目的是保证分析不跳步，不是完整 UML 工序。

1. 列参与者与目标（谁 → 想达成什么）。
2. 写用例主成功场景（3–7 步）+ 关键异常分支。
3. 从用例名词提炼候选概念，定 Entity / 值对象。
4. 按一致性需求划聚合边界，标聚合根。
5. 用顺序图验证主场景的消息协作是否成立。
6. 交接给设计：职责分配与接口契约不在本步完成（回到 `grasp.md` / `contracts.md`）。
7. 用测试或原型验证；暴露的需求缺口回第 1 步。

## 7. UML 何时不必画

- 需求一句话能说清、单一主场景 → 用例文字足够，不必画图。
- 概念少（≤5 个）且关系线性 → 代码即模型，不必画类图。
- 主场景无分支、调用是直线 → 顺序图不提供额外信息。
- 判据：画图能否回答一个当前悬而未决的问题？否 → 不画。图是沟通与验证工具，不是交付物。
- 必须画：跨团队对齐协作拓扑、聚合边界有争议、时序分支复杂到文字说不清。
