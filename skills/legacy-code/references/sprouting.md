## 1. 四种 Sprout / Wrap 手法

### Sprout Method（长芽方法）

- **目的**：新增逻辑写成独立方法，老方法只加一行调用。
- **步骤**：新方法独立写测试 → 老方法内插入调用点 → 老方法本身保持原结构。
- **适用**：老方法还能读、要加的是**新分支/新计算**。
- **反例**：老方法内部已经三重嵌套，再插一行只会加深混乱 → 先 Wrap 或 Direct Edit。

### Sprout Class（长芽类）

- **目的**：新增职责整体放进新类，老类只持有一处委托。
- **步骤**：新类从零写测试 → 老类构造/调用处注入 → 老类逻辑不扩散。
- **适用**：新增的是**独立关注点**（新格式、新协议、新规则集）。
- **反例**：新类需要老类大量私有状态才能工作 → 说明职责切错，改 Wrap Class。

### Wrap Method（包装方法）

- **目的**：老方法原样保留，外面包一层做前置/后置处理。
- **步骤**：老方法改名（如 `doWorkInternal`）→ 新同名方法先处理依赖再委托 → 测试打在新入口。
- **适用**：要在既有逻辑**前后**加副作用（日志、埋点、事务、缓存）。
- **反例**：包装层里塞判断逻辑 → 变成第二份业务规则，应 Direct Edit 拆解。

### Wrap Class（包装类）

- **目的**：第三方/难测类包一层，依赖隔离在包装器内。
- **步骤**：定义接口 → 包装器实现接口并委托真实对象 → 调用方依赖接口，测试传替身。
- **适用**：**不可修改的外部依赖**（SDK、全局单例、硬编码资源）。
- **反例**：包装器只是逐方法转发且无隔离收益 → 中间人，直接注入接口即可。

## 2. 何时必须 Direct Edit

满足任一条即放弃 Sprout/Wrap，直接在老代码上小步改：

- 腐败点本身就是要改的目标（条件分支错、职责错位、算法错），绕开等于不修根因；
- Sprout 后新代码必须读老代码的私有状态/中间变量才能工作；
- Wrap 层无法隔离依赖（依赖在方法体中部，无接缝可插）；
- 同一处已经 Sprout 过两次，第三次说明该处结构本身要重组。

Direct Edit 的前提：**L2 安全网已全绿**，且遵守 L3 两顶帽子（先结构、后语义）。

## 3. 与 L1 的对应

```
L1 选改法
 ├─ 新增逻辑，老方法可读        → Sprout Method  → 跳过 L2，直接 TDD
 ├─ 新增独立关注点              → Sprout Class   → 跳过 L2，直接 TDD
 ├─ 前后加副作用                → Wrap Method    → 跳过 L2，直接 TDD
 ├─ 隔离不可改的外部依赖        → Wrap Class     → 跳过 L2，直接 TDD
 └─ 腐败点即目标 / 上述皆不适用 → Direct Edit    → 必须走 L2 → L3 → L4
```
